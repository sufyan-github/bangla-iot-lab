# Technical requirements

Source: the owner's master build brief (November 2026). This document restates
it as testable requirements and records which phase delivers each one.
Status values: **Done** (implemented and tested), **Partial**, **Planned**.
"Done" means built and covered by automated tests on a laptop and in an
emulated phone; nothing is deployed, and nothing has been checked on real
hardware or a real low-end phone yet.

Statuses brought up to date on 25 November 2026, against the code, the
[progress report](../progress.md) and the [decision log](../decisions/decision-log.md).

## 3. Non-functional requirements

| ID  | Requirement                                            | How it is met or will be verified                                                                                                                                                                                                                                                                                                 |
| --- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| N-1 | Simulation logic is separate from UI                   | `packages/*` may not import React, Fastify, Drizzle or Dexie (ESLint rule); simulation runs in a Web Worker                                                                                                                                                                                                                       |
| N-2 | Simulation accuracy is never asserted without evidence | Checked against ngspice on 33 reference circuits, 30 steady-state and 3 over time (D-091); limits documented in simulation.md                                                                                                                                                                                                     |
| N-3 | Untrusted code never runs in the API process           | Separate compile worker; per-job bubblewrap sandbox; escape tests                                                                                                                                                                                                                                                                 |
| N-4 | Minimal personal data about children                   | Learner rows cannot hold email or roles (database CHECK constraints, tested); a child's own account keeps a guardian's email apart from the child's row; the owner sees a guardian's email only in part; a retention job empties closed accounts and removes old data by proposed periods, not yet confirmed or scheduled (D-101) |
| N-5 | Server-side authorisation for every role               | Done for every route: learners, teachers, school admins and owners, each tested against the API. The API is not deployed                                                                                                                                                                                                          |
| N-6 | Offline first                                          | PWA precache; IndexedDB; a browser test reloads with the network disabled                                                                                                                                                                                                                                                         |
| N-7 | Low-end Android performance                            | Phase 4 target: usable on a 2 GB RAM phone. Not yet measured on a real phone; the owner's office and Kumo load only for owners, so students' downloads did not grow (D-099)                                                                                                                                                       |
| N-8 | Accessibility                                          | Visible focus, 44 px touch targets, reduced-motion support, status messages announced, dark mode. Keyboard operation of the canvas and an automated audit are Planned                                                                                                                                                             |
| N-9 | No fake functionality                                  | No control is rendered unless it works; unavailable actions are disabled with a reason                                                                                                                                                                                                                                            |

## 4. Out of scope for the initial release

Kubernetes, microservices, native Android, AR/VR, public chat, direct messages,
comments, followers, unrestricted student image upload.

ESP32 emulation was out of scope in the first brief; the owner's approval of
the ESP32-first plan brought it in (see the [ESP32 study](../decisions/esp32-study.md)).

## 5. Constraints and assumptions

- Node.js 22 LTS is used for now; the brief names Node 26 (see decision D-001).
- Fully offline C++ compilation is not promised; compiling needs the server.
- Real pilot-school work (Phase 3), legal review and payment registration are
  human activities this repository can only prepare for.
- No email provider is chosen yet: the API refuses to start in production
  until one is (D-096).
