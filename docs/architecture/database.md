# Database design

PostgreSQL 18, Drizzle ORM. Schema source: `apps/api/src/db/schema.ts`.
Migrations: `apps/api/drizzle/` (SQL, checked in).

## Principles

1. **Learners are pseudonymous.** A learner account has no email, phone or real
   name. `CHECK` constraints forbid storing an email or a platform role on a
   learner row; a test proves the database refuses it.
2. **Aggregate before individual.** Teacher reporting reads `class_summaries`
   (planned), not raw per-learner event streams.
3. **Nothing is hard-deleted by request handlers.** Rows are archived, revoked
   or soft-deleted; a retention job purges them later.
4. **UUIDv7 primary keys**, generated by the database (`uuidv7()`), so keys are
   unguessable yet index-friendly. `audit_logs` uses a `bigint` identity.
5. **Foreign keys default to `RESTRICT`.** `CASCADE` only where the child has no
   meaning alone (`project_versions`); `SET NULL` where history must survive (`audit_logs`).

## Implemented in Phase 0 (migration `0000_initial_schema`)

| Table                | Purpose                                | Keys and constraints                                                               |
| -------------------- | -------------------------------------- | ---------------------------------------------------------------------------------- |
| `schools`            | A school                               | PK `id`; unique `eiin`                                                             |
| `users`              | Adults and learners                    | PK `id`; unique `lower(email)`; learner has no email; learner has no platform role |
| `school_memberships` | Role of a user in a school             | unique `(school_id, user_id, role)`; index `user_id`                               |
| `classes`            | A teacher's class                      | FK school, teacher; `grade` between 6 and 12; unique `join_code_hash`              |
| `class_enrollments`  | Pseudonymous learner access to a class | unique `(class_id, learner_id)`; unique `(class_id, pseudonym)`                    |
| `consent_records`    | Guardian or school consent per scope   | index `(learner_id, scope)`; revocable; no school only for a guardian's consent    |
| `projects`           | A saved circuit                        | index `(owner_id, updated_at)`; soft delete                                        |
| `project_versions`   | Immutable snapshots for sync           | unique `(project_id, version)`; `version > 0`; cascades with project               |
| `audit_logs`         | Security-relevant actions              | index `occurred_at`, `(actor_id, occurred_at)`; actor set null on delete           |

Enums: `account_kind`, `platform_role`, `school_role`, `consent_scope`, `consent_grantor`.

## Added with the lab office (migration `0007`, D-097)

| Table / column       | Purpose                                                       | Keys and constraints                                                                  |
| -------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------- |

Migration `0009` (D-100) adds `close-account` to the kinds of email link: a
guardian's one-time link to close a learner's own account. A closed account has

its consent records marked revoked.

## Data retention (proposed; needs owner and legal confirmation)

| Data                           | Retention                                                                                    |
| ------------------------------ | -------------------------------------------------------------------------------------------- |
| Learner account and enrolments | Until the school removes the learner, or 12 months after the class is archived               |
| Projects and versions          | Life of the account; soft-deleted projects purged after 30 days; keep the newest 20 versions |
| Progress events                | Current academic year plus one, then only aggregates                                         |
| Consent records                | Life of the account plus 3 years (evidence of consent)                                       |
| Guardian's email               | Life of the learner's account; then deleted with it                                          |
| Email links (`email_tokens`)   | 30 days after they are used or run out                                                       |
| Audit logs                     | 24 months                                                                                    |
| AI usage records               | 24 months (billing)                                                                          |
| Payments                       | As tax law requires                                                                          |

## Migration strategy

- Change `schema.ts`, run `pnpm db:generate`, review the generated SQL, commit both.
- `pnpm db:migrate` applies pending migrations; it is idempotent (tested).
- Forward-only. Destructive changes use expand → backfill → contract across
  releases so the previous application version keeps working during a deploy.
- Never edit a migration that has been applied anywhere.

## Backup strategy (to be implemented in Phase 4–5)

- Continuous WAL archiving plus a nightly base backup, encrypted, in a second region.
- Targets: recovery point 5 minutes, recovery time 1 hour.
- A restore is rehearsed into a scratch database on a schedule and before every
  release that contains a migration; a backup that has never been restored does not count.

## Not yet enforced

- `audit_logs` is append-only by convention; a trigger or a role without
  `UPDATE`/`DELETE` will enforce it when accounts arrive.
- Row-level tenant isolation is done in application code (Phase 2); PostgreSQL
  row-level security will be evaluated then.
